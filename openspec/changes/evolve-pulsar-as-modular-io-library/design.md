## Context

见 `proposal.md` 的动机与范围。现有 Pulsar 是独立 Git 子模块和单个静态库，公开 `Pulsar::pulsar`，其 IOManager 同时承载 Scheduler、Timer 和 epoll；Hook 仅在 Scheduler Worker 中自动启用。StrataKV 现有 `stratakv_rpc` 依赖 Muduo RpcProvider、同步 MprpcChannel、公共 `util.h` 和项目构建环境；Channel 使用 `poll`、四连接池和整次调用的连接锁，服务端使用 32 个线程容纳会同步等待 Raft 的处理函数。不能把这些文件移入 Pulsar 就认为获得了协程化 RPC。

当前工作树含有无关未提交改动。实施应在可恢复的隔离 checkout 中进行，基线必须记录确切源码状态和测试环境。历史报告仅是参考，不能代替本次前后对照。

## Goals / Non-Goals

**Goals:**

- 以层次清楚的可选目标交付核心、显式网络接口和 Protobuf RPC，让独立示例可构建、安装和运行。
- 保持现有 Pulsar 公开源码接口、导出目标和 StrataKV 默认服务路径；所有新能力须显式选择。
- 把旧 RPC v1 线协议作为互通模式，并以独立测试证明新旧端点互通。
- 把正确性、资源上限、性能门槛和回滚条件设为发布门槛。

**Non-Goals:**

- 本阶段不改 StrataKV 的 Raft、MVCC、2PC、SDK、NodeServer、RpcProvider 或同步 Channel 生产路径；不迁移业务 `.proto`。
- 不为“像 Photon”而复制其模块清单；文件 I/O、io_uring、HTTP/TLS、跨平台和生产级声明另立后续变更。
- 不在 RPC v1 上加入多路复用；如需请求 ID，应另定版本化 v2 协议。

## Decisions

### 1. 模块与依赖方向

保留原静态库及 `Pulsar::pulsar` 导出，新增显式可选的 `Pulsar::net` 和 `Pulsar::rpc` 目标，依赖方向为 `rpc → net → pulsar`。核心不依赖 Protobuf、Muduo 或 StrataKV；RPC 目标可依赖 Protobuf。构建选项默认关闭新目标，安装包只导出实际构建的目标。下游独立 CMake 示例同时覆盖源码子目录和 `find_package(Pulsar CONFIG REQUIRED)`。

备选是把网络/RPC 全部并进原库；这会改变默认依赖和静态库链接图，削弱“默认路径无影响”的保证，因此不采用。也不在本阶段拆开已有 IOManager 的继承结构；新模块适配现有公开接口，避免改动核心热路径。

### 2. 显式网络 API 与资源所有权

每个独立网络服务实例拥有一个配置好的 IOManager 和一个监听 socket。每个已接入的 fd 由唯一连接对象 RAII 持有；连接对象持有读/写状态与有界缓冲，读写等待记录原 Worker。同一个 fd 同一方向只允许一个在途等待，避免 IOManager 的单 READ/WRITE 事件槽被重复注册。显式网络对象使用非阻塞 fd 和自己的 EAGAIN→事件等待循环，避免同时由旧 Hook 与新对象注册同一 fd。连接上限、在途请求上限和缓冲字节上限在接入前检查；达到上限时停止接入或返回过载结果。单个读/写操作由就绪、超时、关闭三者中恰好一个完成，败者不得再次调度同一 Fiber。服务停止顺序为停止 accept、拒绝新请求、取消等待、排空已完成响应、关闭连接、停止 IOManager。

备选是继续只依赖 dlsym Hook 包装同步 socket；Hook 有线程局部启用条件，且不能表达连接级背压、关闭所有权和显式超时语义，故作为兼容入口保留，新增 API 采用显式网络对象。常规文件 I/O 与 DNS 查询不能在 I/O Worker 上直接阻塞；DNS 可预解析或交给有界阻塞执行器。

### 3. RPC 协议与执行模型

RPC 模块包含通用帧编解码、Protobuf Service/Channel 适配及连接管理。v1 请求保持 `[varint32 header_size][RpcHeader][args]`，响应保持 `[network-order uint32 length][serialized response]`；沿用 64 KiB 头和 64 MiB 消息上限。v1 无请求 ID，每连接只允许一个在途调用；客户端可以用有界连接池并发。发送部分字节后断线返回“结果未知”，传输层绝不自动重试；leader 变化、幂等性和业务重试仍由应用处理。

RPC I/O 由 Pulsar Worker 处理。同步服务处理由有界 pthread 执行器承载，队列满时明确拒绝，避免耗尽 I/O Worker。一次请求的解析数据、响应对象和完成状态由共享请求上下文持有；`done` 可以从处理线程或其他业务线程完成，但必须经线程安全队列将发送任务交回连接所属 I/O Worker。连接使用 generation/弱引用避免超时、重连或关闭后向旧 fd 发送。每个请求只允许一次完成，服务注册契约要求最终调用一次 `done`；停止时先排空或报告仍未完成的回调，再销毁服务及提供者。

RPC v1 的 `RpcHeader` 与 StrataKV 旧库若各自生成同名 Protobuf 符号，不能链接到同一测试进程；互通测试启动独立新旧进程，经 socket 交换帧。未来 StrataKV 选择新 RPC 时应替换旧目标而非同时链接两套生成代码。

备选是直接搬入 Muduo RpcProvider，结果仍是 Muduo 服务，无法证明 Pulsar 网络层；也不直接在 Fiber 上运行现有同步 Raft/事务处理函数，其条件变量和磁盘等待会占住 pthread Worker。StrataKV 生产入口继续由当前有界线程池处理。

### 4. 性能与验证口径

先固定代码状态（提交及未提交差异）、机器/CPU 绑定、编译器、构建类型和负载参数，记录至少五轮预热后的原始结果；变更后在同一环境按相同顺序重复。核心门槛覆盖上下文切换、单/多 Worker 调度、Hook echo；StrataKV 门槛覆盖当前 RPC/事务代表性负载的吞吐、P95/P99 和错误数。任何可重复退化都暂停合入并分析；对小于测量噪声的差异只报告区间，不宣称“绝对零开销”。本阶段默认二进制不链接新目标，因此架构上不存在新模块的默认运行时开销。

备选是引用历史 Photon/Pulsar 或跨机器数字，这不能证明当前变更没有回退。

### 5. 对外定位与成熟度表述

第一阶段建议对外描述为“面向 Linux 的 C++17 有栈协程与模块化网络 I/O 库，提供可选 Protobuf RPC”；能力表按“稳定核心、可选实验模块、尚未实现”标注。只有独立构建、故障矩阵和长期负载门槛通过后，才提高对应模块的成熟度表述。来源与许可核查记录保持可见，不用增加模块来暗示全部代码从零原创。

备选是现在直接宣称与 PhotonLibOS 等价的完整 LibOS；现有文件 I/O、平台和生产验证范围不足以支撑这一说法。

## Risks / Trade-offs

- [fd 关闭、epoll 就绪与定时器并发] → 单次完成门闩、原 Worker 恢复、竞态矩阵与压力测试。
- [异步 Protobuf `done` 晚于断连或永不调用] → 请求上下文拥有响应与完成状态，关闭后只释放不发送；强制服务注册契约和有界排空，无法排空时报告失败并保持相关状态存活，避免悬空指针。
- [同步服务占满执行器] → 单独有界线程池、队列上限与过载返回；不与 I/O Worker 或 StrataKV 当前 32 线程池混用。
- [协议 v1 无请求 ID] → 每连接至多一个在途请求；多路复用留待 v2，避免误配响应或悄悄改变协议。
- [发布/来源信息不完整] → 在发布说明中准确陈述实验状态及来源，完成上游版本和许可核查后再选择再分发许可。
- [当前工作树已有改动] → 隔离实施、记录基线、不修改无关文件；回归失败即关闭可选目标并回到原有构建。

## Migration Plan

1. 冻结并复测旧路径基线，保存原始结果；先独立发布模块边界和文档。
2. 在 Pulsar 子模块中加入默认关闭的网络目标及独立示例，验收核心回归后再加入 RPC 目标。
3. 通过新客户端→旧服务端、旧客户端→新服务端的显式互通测试，覆盖半包、超时、重连、重复请求、对端重启及异步回调晚到。
4. 运行 Pulsar 与 StrataKV 功能和同机性能门槛。此阶段只发布可选模块，StrataKV 生产目标仍链接 `stratakv_rpc`。
5. 如任一门槛失败，禁用或撤回可选目标；后续是否让 StrataKV 选用新 RPC，由独立变更与独立 A/B 决定。
